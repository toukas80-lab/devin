Παραδείγματα — **για ίδιο CODE το MTRL (id) είναι πάντα διαφορετικό**:

| CODE | MTRL_1001 | MTRL_3000 |
|---|---|---|
| 00002 | 118333 | 5583 |
| 00009 | 118185 | 4309 |
| 00010 | 118289 | 4270 |
| 00018 | 118284 | 4262 |
| 00019 | 118288 | 4269 |

→ το ταίριασμα 1001↔portal **πρέπει** να γίνεται κατά CODE (όπως ήδη),
όχι κατά id. Τα ids `customer_id`/`item_id` στα prices/invoices/ledger
της 1001 είναι τα 11xxxx της 1001.

`items.json` (1062 CODE): **και τα 1062** υπάρχουν ενεργά στην 1001
και και τα 1062 έχουν webpage (δηλ. θα έμπαιναν όλα στο Q_ITEMS-1001).
Η 1001 έχει επιπλέον **2 codes** με webpage εκτός items.json:
`03509` ΣΟΥΒΛΑΚΟΜΗΧΑΝΗ 169ΤΕΜ 32ΓΡ/ΤΕΜ, `03735` ΙΜΑΝΤΑΣ ΛΕΙΑΝΣΗΣ ULTRA 800Χ50Χ220.

## Συμπεράσματα για export 1001

1. Πελάτες: έτοιμο — 529 τελικοί, 509 κοινοί με την 3000 κατά ΑΦΜ.
   Θέλει απόφαση για τα 3 διπλά ΑΦΜ + τους 20 non-3000.
2. Είδη: και τα 1062 του portal υπάρχουν ενεργά στην 1001 (+2 extra).
   **Mapping αυστηρά κατά CODE — τα MTRL ids είναι όλα διαφορετικά.**
3. Απόθεμα/τιμές/τιμολόγια/καρτέλα: δουλεύουν ως έχουν — η 1001 έχει
   δικό της stock (μόνο WHOUSE 1000) και δικά της ids.
4. **Απόκλιση:** η 1001 τιμολογεί και με αποδείξεις λιανικής
   (TFPRMS 131/181) που το τωρινό φίλτρο του Q_INVOICES αγνοεί
   (~416 παραστατικά, ~74k€ στους 36 μήνες).
5. SOSIGNQR υπάρχει και στην 1001 (241 παραστατικά), join ασφαλές.
